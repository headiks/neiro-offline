# RAG-ассистент по регламентам (DeepSeek)

Вся генерация, классификация и поиск идут через облачную модель **DeepSeek**
(`deepseek.py`, ключ `DEEPSEEK_API_KEY`). Локальные LLM (Ollama), эмбеддинги и
векторный стор (Qdrant) не используются: документ разбирается docling на секции, а
DeepSeek размечает их относительно плана адаптации (этапы/подэтапы/профессии); метки
хранятся в PostgreSQL, ретрив — по ним (см. `docpipe/`, `rag.route_substages`).

Аккаунты, сессии, реестр документов, вопросы, планы и сообщения лежат в PostgreSQL
(`docs/storage.md`). Старые `registry.json` и `pending_questions.json` переносятся в БД при старте.

## Страницы и доступ

| Страница | Кто | Что там |
|---|---|---|
| `/` | все, по сессии | Мой кабинет: прогресс адаптации, сообщения плана, история, ассистент, вопросы специалисту, «Я на больничном». На телефоне — как приложение |
| `/login`, `/register`, `/setup` | все | Вход, регистрация (если включена), замена временного пароля |
| `/admin/users` · `/plans` · `/documents` · `/messages` · `/questions` | администратор | Пользователи и штатка, конструктор планов, документы, сообщения сотрудникам, вопросы |
| `/logs` | администратор | Журнал действий |
| `/globaltest` | администратор + пароль раздела | Тесты и диагностика: `/notify-test`, `/message-test`, `/queue-test`, `/s3`, `/plans-db`, `/documents-table`, `/documents-board`, `/doc-breakdown`. Без пароля раздела страницы ведут на `/globaltest`, их API отвечают 403. Пароль — хешем в `NEIROMASTER_GLOBALTEST_PASSWORD_HASH` (`python scripts/globaltest_hash.py`) |

Весь сайт — одно приложение на React (`frontend/`, дизайн Glass: светлая и тёмная темы,
Manrope, стекло). Сервер отдаёт собранный `static/app/index.html` на каждой странице, проверяя
доступ как раньше; маршруты разбирает React Router. После правок интерфейса:
`cd frontend && npm ci && npm run build` и закоммитить `static/app/`.

**Роли.** `owner` (суперадмин) видит документы всех администраторов и всех людей;
`admin` — только свои загрузки и людей своего отдела; `employee` — чат и своё
расписание. Правила собраны в `users.py` (`can_see_doc`, `visible_users`, `can_manage`)
и проверяются тестом `tests/test_roles.py`.

**Как пользоваться.** Пункт **«Как пользоваться»** в настройках (шестерёнка внизу сайдбара; на телефоне — вкладка «Настройки») запускает
интерактивный тур: сайт сам проходит по всем разделам в порядке работы (пользователи → план →
документы → сообщения → вопросы) — подсвечивает элементы, подводит курсор, «нажимает»,
печатает примеры в поля и ничего не сохраняет. Пауза, назад/далее, Esc — выход. При первом
входе тур предлагается сам; `/admin?tour=1` или `/?tour=1` — запустить сразу.

**Первый запуск.** Учётка владельца (суперадмина) создаётся автоматически. Пароль берётся из
переменной окружения `NEIROMASTER_ADMIN_PASSWORD` (от 8 символов), если она задана; иначе
генерируется случайный, печатается в лог сервера и дублируется в
`data/owner_initial_credentials.txt`. При первом входе система попросит задать свой пароль,
после этого файл удаляется.

**Как устроен вход и защита.**
- Пароли — scrypt-хэш с индивидуальной солью. Сессия — токен в httponly-куке (`Secure`,
  `SameSite=Lax`) или Bearer-токен у мобильного приложения. В БД хранится только SHA-256
  токена. Сессия живёт 12 часов без активности и общая для всех воркеров.
- 10 неудачных попыток входа — логин заблокирован на 5 минут (счётчик в Redis, общий для всех
  процессов); плюс лимит попыток входа с одного IP. Новый пароль от администратора снимает блокировку.
- Изменяющий запрос с кукой принимается только со своего сайта (проверка Origin).
- Заголовки: CSP без сторонних доменов и без inline-скриптов (`script-src 'self'`), запрет
  встраивания во фрейм, HSTS. Скрипты, иконки и шрифт — в сборке сайта, внешних запросов нет.
- ФИО, контакты, заметки и вопросы сотрудников зашифрованы в БД; ключ создаётся сам при первом
  старте (`data/secrets/pii.key`) — храните его копию отдельно от бэкапов БД.
- Лимиты: вопрос ассистенту до 2000 символов и 20 в минуту, размеры полей и загрузок.
- Самостоятельную регистрацию можно выключить: `NEIROMASTER_ALLOW_REGISTRATION=0`.
- Подробно: `docs/security-audit.md`; чек-лист выкатки — `docs/production.md`.

Все админские ручки требуют сессии и отвечают 401 без неё. Публичные — только вход,
регистрация, `/api/config` и `/healthz` (проверка живости для мониторинга).

Внутри `data/documents/` уже лежат два тестовых регламента для проверки:
- `reglament_ohrana_truda.docx` — общий регламент по охране труда (СИЗ, инструктажи, отпуска, режим труда)
- `instrukciya_vysota_pozhbezopasnost.pdf` — работа на высоте, пожарная и электробезопасность

## Контекст диалога (история вопросов)

Сайт запоминает последние вопросы пользователя в рамках одной открытой вкладки
браузера (`session_id` живёт в переменной страницы и сбрасывается при
перезагрузке, сама история хранится в памяти сервера). Если новый
вопрос короткий и обрывочный ("Где взять", "А сколько?") — перед поиском и
генерацией ответа `rag.py` анализирует последние до 3 вопросов из
истории и переписывает его в полный самостоятельный вопрос (например, "Где
взять экипировку для работы на высоте?"). Если вопрос уже самодостаточен —
история не используется, лишний вызов модели не тратится.

Кнопка «Новый диалог» у ассистента сбрасывает историю и начинает сессию заново.

## Путь документа до готовности к поиску

```
Загрузка файла (сайт -> фоновая очередь индексации)
        │
        ▼
DocumentConverter (docling) — разбор PDF/DOCX/PPTX/HTML:
структура, заголовки, таблицы, страницы
(DoclingDocument кэшируется в data/processed/*.json —
 повторно тот же файл не парсится)
        │
        ▼
docpipe: деление на секции по заголовкам/пунктам
        │
        ▼
DeepSeek размечает каждую секцию относительно плана адаптации:
этапы, подэтапы, профессии, «общая информация», обоснование (why)
        │
        ▼
PostgreSQL (sections + section_labels) — источник правды.
Ретрив: rag.route_substages выбирает подэтапы -> docpipe.blocks_for_substage
берёт размеченные ими секции. Векторов/эмбеддингов нет.
```

## Запуск в Docker (рекомендуется)

```bash
docker compose up -d
```

Одна команда поднимает всё: сайт за HTTPS (Caddy), web, worker'ы, две PostgreSQL (исходники
`db-raw` и обработанное `db-processed`) и Redis. Настройки, бэкапы, закрытый контур —
[docs/docker.md](docs/docker.md).

## Установка (Linux-сервер без Docker)

Скопируйте папку `project/` на сервер, зайдите в неё по SSH и запустите:

```bash
chmod +x install.sh
./install.sh
```

Работает и от root, и от обычного пользователя с sudo. Скрипт ставит:
apt-пакеты → venv + `pip install -r requirements.txt` → PostgreSQL и Redis в Docker (`--restart unless-stopped`) → systemd-сервисы `rag-app` (сайт) и `rag-worker@N` (фоновая разметка/генерация).

После установки **впишите ключ DeepSeek** в `.env.production` (строка
`DEEPSEEK_API_KEY=...`) — без него генерация и классификация не работают.

**Важные моменты именно для сервера:**
- LLM — облачный DeepSeek, локальные модели не ставятся. Нужен только ключ
  `DEEPSEEK_API_KEY` (получить на platform.deepseek.com) в `.env.production`.
- Эмбеддингов и векторного стора (Qdrant) нет: разбор, классификацию и поиск делает
  DeepSeek через docpipe (LLM-метки этапов/подэтапов в PostgreSQL). Локальные модели
  (bge-m3/Ollama) не нужны.
- Порт PostgreSQL (5432) и Redis (6379) привязаны только к `127.0.0.1` — наружу не торчат, приложение обращается к ним через localhost.
- Сайт запускается как systemd-сервис (`rag-app`), а не фоновым процессом — переживает обрыв SSH-сессии и перезагрузку сервера.
- Роли моделей DeepSeek переопределяются через env (`DEEPSEEK_MODEL` и
  `DEEPSEEK_BIG_MODEL`/`DEEPSEEK_SMALL_MODEL`/`DEEPSEEK_DOCPIPE_MODEL`/…), по
  умолчанию все — `deepseek-chat`.

## Запуск

Документы индексируются автоматически при загрузке через сайт (фоновая очередь) —
отдельного CLI-шага индексации нет.

```bash
# Сайт и воркеры запускаются как systemd-сервисы
sudo systemctl start rag-app 'rag-worker@1'
sudo systemctl status rag-app
sudo journalctl -u rag-app -f      # логи в реальном времени

# Деплой обновления кода:
git pull origin master && sudo systemctl restart rag-app 'rag-worker@*'
```

Сайт слушает `127.0.0.1:8000`; наружу его отдаёт HTTPS-прокси (Caddy, сертификат сам):
```
ваш-домен.ru {
    reverse_proxy 127.0.0.1:8000
}
```
Без HTTPS вход не сохранится: кука сессии помечена `Secure`. Для локальной разработки без
TLS — `NEIROMASTER_INSECURE_COOKIE=1`. Проверка живости: `curl -s http://127.0.0.1:8000/healthz`.

## Как работает загрузка через сайт

1. Пользователь перетаскивает PDF/DOCX в область загрузки на сайте.
2. `POST /documents/upload` сохраняет файл в `data/documents/` (имя очищается от опасных символов, путь traversal исключён) и ставит его в фоновую очередь индексации.
3. Фоновый воркер вызывает `indexing.index_document()` → `docpipe.ingest()`: docling разбирает документ на секции, DeepSeek размечает каждую секцию относительно плана адаптации (этапы/подэтапы/профессии), метки пишутся в PostgreSQL. Векторов/эмбеддингов нет.
4. Прогресс индексации виден на карточке документа; список документов и доска «этапы ↔ документы» обновляются автоматически.
5. Дедупликация по SHA-256: тот же файл (под любым именем) повторно не грузится и не размечается.
   Новая версия с тем же именем — выбор «заменить старую» или «сохранить отдельно».
6. Перед отправкой в DeepSeek текст обезличивается (`pii.py`, `docs/pii.md`): ФИО в любом
   падеже, телефоны, паспорт, реквизиты и т.п. заменяются метками, в ответе — обратно.
7. Чувствительный документ (положение об оплате труда) можно пометить **«Не отправлять в ИИ»**
   (при загрузке или кнопкой у документа): он хранится, но не размечается и не попадает в
   сообщения и ответы.
8. Кнопка «Удалить» у документа убирает разметку docpipe (каскадом секции/метки/чанки в PostgreSQL), сам файл, S3-копию и кэш docling.

## Привязка документов к этапам и подэтепам

Отдельной раскладки по «папкам» на основе эмбеддингов больше нет. Привязку даёт
LLM-разметка docpipe: при индексации DeepSeek для каждой секции документа решает, каким
подэтапам плана адаптации она ПРЯМО соответствует (с обоснованием why и пометкой «общая
информация»). Из этих меток строятся:

- доска «этапы ↔ документы» (`GET /documents/board`, `documents.build_board`);
- контекст генерации плана и ответов на вопросы (`docpipe.blocks_for_substage`).

Смысловые папки (`folders.py`) остаются как ручные категории базы знаний — их заводит и
редактирует человек; они не участвуют в ретриве по подэтапам.

## Конструктор плана адаптации (вкладка «🗓️ Конструктор плана»)

Человек собирает расписание сообщений новому сотруднику, система генерирует тексты по документам.

**Как собирается план**

1. Этапы выбираются из каталога `data/stage_catalog.json` (8 этапов: предварительная
   адаптация, первый день, первая неделя, стажировка, проверка знаний и допуск, начало
   самостоятельной работы, интеграция, итоги). Каталог намеренно профессионально-независимый:
   специфика должности приходит из документов, а не из названий этапов. Можно добавить и свой этап.
2. У этапа задаётся длительность: часы / дни / недели / месяцы, и якорь — «до выхода на работу»
   или «от даты выхода».
3. Подэтапы берутся из шаблонов этапа (всего 62 заготовки) либо пишутся вручную. У подэтапа есть
   тип (сообщение, чек-лист, опрос, мини-тест, напоминание, системная проверка, задача человеку)
   и описание того, что должен написать бот — оно и уходит в LLM как задание.
4. Время срабатывания: день внутри этапа (1…N, где N считается из длительности) и время суток.
   Если длительность задана в часах — день не выбирается, только время.

**Как считается дата отправки**

Время хранится относительно даты выхода сотрудника, не абсолютно. Этапы с якорем
«до выхода» выстраиваются подряд так, чтобы последний их день пришёлся на день перед выходом
(смещение −1), этапы «от даты выхода» — подряд начиная с дня выхода (смещение 0). Абсолютные
дата и время получаются подстановкой `start_date`, поэтому один и тот же план переиспользуется
для любого новичка.

**Стандартный план и частота сообщений.** Пункт «Стандартный план» в списке планов создаёт
план из всего каталога (≈3 месяца), подэтапы в нём разнесены по дням этапа. Галочка
«Сообщения одного дня — одной сессией» (`group_daily`) присылает все сообщения дня вместе —
во время первого из них и одним уведомлением.

**Несколько администраторов.** Если план успел изменить другой администратор, сохранение не
затрёт его правку молча: сервер вернёт 409, интерфейс предложит сохранить поверх или загрузить
актуальную версию.

**Генерация автоответов**

`POST /plans/{id}/generate` запускает фоновую задачу; фронтенд тянет прогресс через
`GET /jobs/{job_id}`. По каждому подэтапу:

```
подэтап (catalog_id "<этап>.<подэтап>") + должность сотрудника
        │
        ▼
гейт: есть ли документ, размеченный этим подэтапом (docpipe)?
нет -> подэтап «пропущен» (ждёт загрузки документа и догенерации)
        │
        ▼
docpipe.blocks_for_substage — секции, размеченные этим подэтапом (PostgreSQL),
режутся под бюджет контекста модели
        │
        ▼
DeepSeek пишет готовое сообщение сотруднику строго по фрагментам
```

Отдельный подэтап можно перегенерировать, не прогоняя весь план:
`POST /plans/{id}/messages/{message_id}/regenerate`.

**Что на выходе**

| Файл | Что это |
|---|---|
| `plan.json` | Канонический план — источник истины, из него всё считается |
| `plan.md` | Тот же план в удобном для LLM виде |
| `schedule.json` | Плоский список сообщений с временем отправки — формат под мессенджеры и самописное приложение |
| `schedule.md` | Человекочитаемая таблица этап / подэтап / дата и время / ответ |

Одно сообщение в `schedule.json`:

```json
{
  "message_id": "st1_pre_onboarding.s1_greet_intro",
  "stage":    { "id": "st1_pre_onboarding", "order": 1, "title": "Предварительная адаптация" },
  "substage": { "id": "s1_greet_intro", "order": 1, "title": "Приветствие", "kind": "message" },
  "schedule": { "anchor": "before_start", "stage_day": 1, "time": "10:00",
                "offset_days": -3, "send_at": "2026-08-29T10:00" },
  "content":  { "format": "markdown", "text": "Добрый день, [Имя]! ..." },
  "actions":  [],
  "folders_used": ["Адаптация и наставничество"],
  "sources":  [{ "source": "Положение по адаптации.pdf", "folder": "...", "page": 3, "score": 0.87 }],
  "status": "generated"
}
```

Формат специально плоский и самодостаточный: планировщику мессенджера нужны только
`send_at` (или `offset_days` + `time`, если дата выхода подставляется в момент найма),
`content.text` и `message_id` для идемпотентности. Поле `actions` зарезервировано под
кнопки и варианты ответа сотрудника.

**Ручки конструктора**

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/catalog` | Каталог этапов и шаблонов подэтапов |
| GET | `/folders` | Смысловые папки с числом документов |
| GET/POST | `/plans` | Список планов / создание |
| GET/PUT/DELETE | `/plans/{id}` | Чтение (с превью расписания) / обновление / удаление |

## Сотрудники и назначение планов (вкладка «👥 Сотрудники»)

Администратор заводит сотрудника, выбирает готовый план-шаблон и дату выхода на работу.
Персональное расписание считается на лету:

```
план (относительные смещения)
      + дата выхода сотрудника        -> конкретные дата и время каждого сообщения
      + сгенерированные тексты плана  -> содержимое сообщений
      + данные сотрудника             -> подстановка [Имя], [ФИО наставника], [Должность]
```

Тексты под каждого сотрудника заново не генерируются: они зависят от документов компании,
а не от человека. Один сгенерированный план обслуживает сколько угодно новичков — меняются
только даты и плейсхолдеры. Правка плана или даты выхода сразу отражается в расписании,
пересчёт вручную не нужен.

Поля сотрудника: ФИО, должность, подразделение, контакт, наставник, руководитель,
назначенный план, дата выхода, статус (`planned` / `active` / `paused` / `done`), заметки.
Наставник и руководитель нужны не только для справки — из них подставляются плейсхолдеры
в текстах сообщений.

Если у плана ещё не сгенерированы ответы, расписание всё равно покажется: даты рассчитаны,
тексты пустые, и в интерфейсе висит предупреждение.

| Метод | Путь | Назначение |
|---|---|---|
| GET/POST | `/employees` | Список сотрудников / создание |
| GET/PUT/DELETE | `/employees/{id}` | Чтение / обновление / удаление |
| GET | `/employees/{id}/schedule` | Персональное расписание (пересчитано на дату выхода) |
| GET | `/employees/{id}/export/{schedule.md\|schedule.json}` | Скачивание персонального расписания |
