# Аудит безопасности и подготовка к продакшену

Что проверяли: все маршруты API (права по ролям и подразделениям), вывод данных в
интерфейсе (XSS), загрузку файлов и пути, сессии и вход, CSRF, заголовки ответа, внешние
зависимости страниц, отправку данных в DeepSeek, лимиты и отказоустойчивость. Каждое
исправление закреплено тестом (`test_api_integration.py`, `test_pii.py`, `e2e_test.py`).

## Найдено и исправлено

| # | Уровень | Что было | Что стало |
|---|---|---|---|
| 1 | **Критично** | ID этапов и подэтапов плана принимались от клиента как есть и попадали в `onclick="…('${id}')"` админки. Администратор мог сохранить план с ID-скриптом, и тот выполнялся в сессии суперадмина (повышение прав). Экранирование HTML не спасало: браузер раскодирует `&#39;` в атрибуте до запуска JS | ID очищаются на сервере (`planner._safe_id`: буквы, цифры, `_`, `-`). Во фронтенде аргументы обработчиков передаются через `jsArg()` (JS-литерал + экранирование атрибута) |
| 2 | **Критично** | `escapeHtml`/`esc` на всех страницах не экранировали кавычки: значение из штатки или самостоятельной регистрации (должность, ФИО) могло выйти из атрибута `value="…"` | Экранируются `& < > " '` на всех 12 страницах |
| 3 | **Высокий** | `DELETE /users/{id}`: обычный администратор мог удалить сотрудника **чужого** подразделения | Одно правило для одиночного и массового удаления (`_delete_denied`) |
| 4 | **Высокий** | Администратор мог сменить **себе** подразделение и увидеть людей чужого отдела; мог заводить людей в чужие отделы | Отдел обычному админу не меняется ни себе, ни сотрудникам; новые люди и импорт штатки — только в свой отдел |
| 5 | **Высокий** | Экспорт «логины и пароли» в Excel: ФИО вида `=HYPERLINK(...)` из штатки становилось формулой (Excel/CSV-инъекция) | Значения, начинающиеся с `= + - @`, экранируются апострофом, ячейки строковые |
| 6 | Высокий | Токены сессий лежали в БД открытым текстом: утёкший дамп = вход под любым пользователем | В БД хранится SHA-256 токена. Старые сессии переводятся на хэш при первом обращении — никого не разлогинивает |
| 7 | Высокий | Защита от перебора пароля жила в памяти **каждого** воркера (при 6 воркерах — 60 попыток вместо 10) | Счётчик в Redis, общий для всех процессов; + лимит попыток входа с одного IP |
| 8 | Высокий | Внешние скрипты с `unpkg.com/lucide@latest` (без версии и проверки целостности) и шрифты Google на всех страницах: подмена пакета = выполнение кода в админке; запросы раскрывают IP сотрудников третьей стороне | Lucide 1.48.0 и шрифты Fira Sans лежат в `static/vendor/`. Страницы не ходят на сторонние домены |
| 9 | Средний | Нет заголовков безопасности: сайт можно было встроить во фрейм (clickjacking), не было CSP | `security.py`: CSP (`script-src 'self'`, `connect-src 'self'`, `frame-ancestors 'none'`), `X-Frame-Options`, `nosniff`, `Referrer-Policy`, HSTS при HTTPS, `Cache-Control: no-store` для ответов с данными |
| 10 | Средний | CSRF держался только на `SameSite=Lax` | Вторая линия: изменяющий запрос с кукой сессии принимается только со своего Origin |
| 11 | Средний | `/ask` без ограничений: вопрос любой длины и частоты = неограниченный расход токенов DeepSeek | Вопрос до 2000 символов, до 20 вопросов в минуту на пользователя |
| 12 | Средний | Чужой `session_id` диалога подмешивал в контекст переписку другого человека | Сессия диалога привязана к владельцу, чужая — не принимается |
| 13 | Средний | Сотруднику в ответе `/ask` уходили сырые фрагменты регламентов (`top_fragments`) | Фрагменты — только администраторам (для отладки) |
| 14 | Средний | `POST /documents/..%2F/reprocess`: имя файла из URL шло в путь без проверки | Действия над документом — только по имени из реестра |
| 15 | Средний | Выход из мобильного приложения не отзывал Bearer-токен | `/api/logout` отзывает тот токен, которым пришли (кука или Bearer) |
| 16 | Средний | `DELETE /api/my/push-token` отвязывал **любой** токен, в том числе чужого устройства | Только свой |
| 17 | Низкий | Без лимитов размера: ответы на чек-листы, тексты плана, длительность этапа (`10^9` дней -> переполнение дат -> 500), журнал кликов | Ограничения в моделях запросов и `normalize_plan`, лимит частоты журнала |
| 18 | Низкий | Регистрацию нельзя было выключить в закрытом контуре; нет лимита частоты (спам аккаунтами + нагрузка scrypt) | `NEIROMASTER_ALLOW_REGISTRATION=0`, 5 регистраций в час с IP |
| 19 | Низкий | Gunicorn из `install.sh` слушал `0.0.0.0:8000`: сайт был доступен по открытому HTTP в обход HTTPS-прокси | `127.0.0.1:8000` по умолчанию, наружу — только через Caddy/nginx |

## Найденные попутно ошибки в работе

| Что было | Что стало |
|---|---|
| Даты выхода из штатки `.xls`/`.csv` приходили как `15.05.2026`: расписание не строилось, **сообщения не приходили**, статус навсегда «Запланирован», при сохранении карточки дата стиралась | Даты приводятся к `ГГГГ-ММ-ДД` при любой записи; старые записи исправляются миграцией при старте |
| Дедупликация при загрузке смотрела в таблицу, которую никто не заполнял: тот же файл под другим именем **заново оплачивался** полной разметкой | SHA-256 содержимого в реестре + поиск по хэшу разметки для старых документов |
| «Сохранить отдельно» давало имя `Регламент (2).pdf`, санитайзер делал из него `Регламент _2_.pdf`, и следующая отдельная копия затирала предыдущую | Скобки в именах файлов разрешены |
| Сбой генерации одного подэтапа стирал его прежний текст | Не пересчитанные подэтапы сохраняют прежний текст |
| Двойное нажатие «Обновить сообщения» могло запустить две платные генерации (гонка на время оценки) | Атомарный замок запуска (`jobstore.claim`) |
| Доска документов падала с `ReferenceError`, если к этапу привязан документ без подэтапа | Исправлено |
| Кэш ответов считал «не» стоп-словом: «выдали пропуск?» и «не выдали пропуск» — один ответ | Отрицания значимы |
| Реестр документов и вопросы сотрудников лежали в JSON-файлах: общий на все кабинеты (кабинеты разных компаний видели бы документы друг друга), блокировка на весь файл, не работает на нескольких серверах | Таблицы `doc_registry` и `questions` в PostgreSQL (в схеме кабинета), обновление атомарное; файлы переносятся при старте |
| Планировщик раз в минуту расшифровывал и перебирал всех пользователей | Отбор нужных сотрудников в SQL |
| `seen_at` сессии писался в БД на **каждый** запрос | Не чаще раза в минуту |
| `NEIROMASTER_ADMIN_PASSWORD` из README игнорировался кодом | Работает (от 8 символов) |
| CSP разрешал inline-скрипты (`'unsafe-inline'`): внедрённый в страницу `<script>` выполнился бы | Сайт переписан на React без inline-скриптов и HTML-вставок; `script-src 'self'` (тесты проверяют) |
| Шифрование ПДн в БД включалось только ключом из окружения — на сервере без ключа ФИО лежали открытым текстом | Ключ создаётся сам (`pii_key.py`), старые строки шифруются на старте, чужой/потерянный ключ останавливает старт |

## Что осталось на решение людей

- **Правильные ответы мини-тестов** уходят в приложение вместе с вопросом (отметка «верно»
  нужна для мгновенной проверки). Если тесты станут аттестацией, проверку надо перенести на сервер.
- **`style-src 'unsafe-inline'`** остаётся: React задаёт часть стилей атрибутом `style`.
  Исполнение скриптов это не открывает.
- **Шифрование ПДн в БД** включено всегда: ключ создаётся сам (`pii_key.py`,
  `data/secrets/pii.key`), открытые строки, записанные раньше, шифруются на старте. Копию
  файла ключа нужно хранить отдельно от бэкапов БД (см. `docs/production.md`).
- **NER для ПДн** (Natasha/Slovnet) — если на реальных документах заказчика регулярные
  выражения и словарь что-то пропускают (см. `docs/pii.md`).
